## ✅ 1. Blocage des inputs réels vers les instances Dolphin

### Problème (v0.5.0)
```rust
// lib.rs : quand l'agent n'était pas actif, les vrais inputs
// de l'utilisateur pouvaient traverser jusqu'à Dolphin
if !HOOK_ACTIVE.load(Ordering::Relaxed) {
    return match ORIG_GET_DEVICE_STATE { Some(orig) => orig(...) };
    // ↑ Les vrais inputs passaient sans filtre
}
```

### Maintenant (v0.5.5)
```rust
// lib.rs — Blocage total des inputs physiques dès que le hook est actif
// Keyboard (cb_data=256) : toujours zéro sauf shared memory
for i in 0..256usize {
    if *SHARED_MEM_PTR.add(i) != 0 {
        *lpv.add(i) = 0x80;  // Injecté depuis AI
    } else {
        *lpv.add(i) = 0;     // Explicitement bloqué (pas pass-through)
    }
}
// Mouse buttons : même logique via MOUSE_OFFSET
// → L'utilisateur peut taper sur son clavier sans que Dolphin le reçoive
```

**Impact :**
- ✅ L'utilisateur peut travailler normalement (écrire du texte, etc.)
- ✅ Les touches de l'utilisateur n'interfèrent plus avec les agents
- ✅ Isolation garantie même si l'utilisateur clique accidentellement sur la fenêtre Dolphin

## ✅ 2. Save states via `send_save_state_key()` (PostMessage)

### Problème (v0.5.0)
Les save states (F5, F6...) ne fonctionnaient plus car :
1. `GetAsyncKeyState` était intercepté et retournait 0 pour toutes les touches
2. Le hook bloquait les F-keys avant qu'elles atteignent Dolphin

### Solution (v0.5.5)
```rust
// lib.rs — F1-F8 passent à travers GetAsyncKeyState (Dolphin Qt HotkeyManager)
unsafe extern "system" fn hooked_GetAsyncKeyState(vk: i32) -> i16 {
    if vk >= 0x70 && vk <= 0x77 {
        // F1-F8 : pass-through vers le vrai GetAsyncKeyState
        return match ORIG_GET_ASYNC_KEY_STATE { Some(orig) => orig(vk), None => 0 };
    }
    // Autres touches : bloquées (0) si hook actif
}
```
```python
# wii_controller.py — send_save_state_key() utilise PostMessage vers render window
def send_save_state_key(self, key_name: str) -> bool:
    """Envoie WM_KEYDOWN/WM_KEYUP directement à la fenêtre MHTri-N."""
    vk_code = VK_FKEYS[key_lower]
    win32api.PostMessage(self._render_hwnd, win32con.WM_KEYDOWN, vk_code, 0)
    time.sleep(0.2)
    win32api.PostMessage(self._render_hwnd, win32con.WM_KEYUP, vk_code, 0)
```

## ✅ 3. Correction : boutons souris non fonctionnels (mouse_left, mouse_right)

### Problème (v0.5.0)
```python
# constants.py — OLD : mouse buttons utilisaient '&0xFF' qui tronquait à 255
# MOUSE_LEFT = 256 → (256 & 0xFF) = 0 → jamais injecté !
def _set_key(self, dik: int, pressed: bool):
    if self.buf and 0 <= dik < 256:  # ← limitait à 255
        self.buf[dik] = 1 if pressed else 0
```

### Maintenant (v0.5.5)
```python
# constants.py — Offsets dédiés pour les boutons souris après les 256 bytes clavier
MOUSE_LEFT  = 256  # Byte index 256 dans shared memory (A button / attack)
MOUSE_RIGHT = 257  # Byte index 257 (B button / dodge)

# wii_controller.py — _set_key() accepte maintenant les index > 255
def _set_key(self, dik: int, pressed: bool):
    if self.buf and 0 <= dik < SHARED_MEM_SIZE:  # SHARED_MEM_SIZE = 280
        self.buf[dik] = 1 if pressed else 0

def _press(self, key: str):
    if key == 'mouse_left':
        self._set_key(MOUSE_LEFT, True)   # Index 256
    elif key == 'mouse_right':
        self._set_key(MOUSE_RIGHT, True)  # Index 257
    elif key in DIK:
        self._set_key(DIK[key], True)
```

**Impact :** Les attaques (mouse_left) et esquives (mouse_right) fonctionnent maintenant correctement.

## ✅ 5. Recherche fenêtre render window (lazy init)
```python
# wii_controller.py — La render window MHTri-N est cherchée au démarrage
# et re-cherchée si absente (lazy init pour robustesse multi-instance)
if self._render_hwnd is None:
    hwnd = win32gui.FindWindow(None, f"MHTri-{self.instance_id}")
    if hwnd and win32gui.IsWindowVisible(hwnd):
        self._render_hwnd = hwnd  # Trouvée en retard (late init)
```
